## 3. Ce qui a été fait, étape par étape

### 3.1 Comprendre CUAD (notebook d'exploration)

**But** : connaître les données **avant** de construire un modèle. Le notebook répond à 8 questions
(a à h). Il est commité **sans ses sorties**, parce qu'elles affichent du texte de contrats et que le
dépôt est public (règle 5).

Résultats :
- **a.** 510 contrats, 41 catégories, 13 823 passages. Chaque position `answer_start` retombe
  exactement sur le passage annoté (13 823 / 13 823) → les positions sont fiables.
- **b.** Contrats de 645 à 338 211 caractères, médiane 33 143 : bien trop longs pour un Transformer
  (≈ 2 000 caractères à la fois) → il faut découper en **segments** (D-001).
- **c.** Nos 9 catégories vont de 470 contrats (*Agreement Date*) à 111 (*Uncapped Liability*).
- **d, e.** Durée = souvent des dates courtes (médiane 16 caractères) ; responsabilité et
  résiliation = des clauses entières (plusieurs centaines de caractères).
- **f. Découverte 1** : 125 des 167 passages *Uncapped Liability* sont **exactement** des passages
  *Cap On Liability*. C'est souvent **une seule clause** (une limite avec une exception). Donc la
  tâche est **multi-étiquette**, et F3 ne doit pas signaler une « incohérence » pour ça.
- **g. Découverte 2** : l'article annonce 13 101 annotations, le JSON en a 13 823. 13 101 est le
  nombre d'éléments de `master_clauses.csv` ; le JSON découpe en plusieurs passages les annotations
  non contiguës (`<omitted>`). Écart expliqué à 11 passages près.
- **h. Découverte 3** : le texte `context` du JSON est identique au fichier TXT pour les 510 contrats.

### 3.2 Découper les données : train, validation, test (D-004, D-005)

- **Pourquoi** : un modèle s'entraîne sur le *train*, se règle sur la *validation*, et n'est mesuré
  qu'**une fois** sur le *test* à la fin. Si on règle sur le test, le score final est trop beau.
- **Par contrat** : tous les segments d'un même contrat vont dans le même jeu, sinon le modèle
  serait testé sur des phrases « presque déjà vues ».
- **Choix (D-004)** : test = **test officiel** de CUAD (102 contrats, fichier `data.zip` du dépôt
  GitHub, empreinte vérifiée) ; validation = 15 % du train officiel tirés avec la **graine 42**,
  fixée **avant** le tirage ; nos 9 catégories sont présentes dans chaque jeu.
- **D-005** : le fichier des splits (titres seulement) est commité, pour que tout le monde utilise
  les mêmes jeux ; la règle 5 de `CLAUDE.md` a été étendue à `data/splits/`.
- **Garde-fou** : `charger_segments` et `charger_contractnli` **refusent** de lire un jeu de test
  sans `ouvrir_test=True`. Aucun test n'a été ouvert pendant toute la période.

### 3.3 Segments et traçabilité (D-001)

- Un **segment** = un morceau de texte + sa provenance : contrat, page, position de début, position
  de fin. Garantie vérifiée partout : `texte[debut:fin] == texte du segment`.
- **Règle v1** : couper aux lignes vides ; retirer les espaces aux bords en **décalant les
  positions** ; plafond de 1 500 caractères (au-delà, recouper aux sauts de ligne).
- **Projection des annotations** : un segment reçoit une catégorie si son chevauchement avec un
  passage annoté atteint **min(20 caractères, longueur du passage)**. Règle fixée **avant** de voir
  les résultats. Une seule annotation sur 3 257 n'étiquette aucun segment.

### 3.4 Première baseline d'extraction (D-006)

- **Baseline 1 — mots-clés** : une liste écrite à la main à partir des définitions de CUAD, figée
  avant évaluation. Macro-F1 **0,247** : elle trouve beaucoup (rappel 0,68) mais se trompe souvent
  (précision 0,16), car « term », « liable » ou « effective date » sont partout.
- **Baseline 2 — TF-IDF + régression logistique**, un classifieur par famille, pondération des
  classes, réglages (n-grammes, C, seuil) **sur la validation** : macro-F1 **0,669**
  (durée 0,727 ; résiliation 0,521 ; responsabilité 0,758).
- **Analyse de 24 erreurs** : 9 viennent d'**étiquettes discutables** (CUAD n'annote pas chaque
  occurrence), 7 de la **segmentation**. La résiliation est la plus difficile : résilier *sans
  motif* et *pour faute* emploient les mêmes mots.

### 3.5 Lire les PDF (D-007, D-008)

- **PyMuPDF** (version 1.x) lit le texte **page par page**. Les pages sont séparées par une ligne
  vide : un segment ne chevauche jamais deux pages, donc **son numéro de page est exact**.
- **Alignement (D-007)** : les annotations CUAD portent sur le texte de CUAD, pas sur le texte du
  PDF. On les **retrouve** dans le texte PDF par une correspondance **exacte** après normalisation
  (espaces, majuscules, guillemets typographiques…), en gardant le lien avec les positions
  d'origine. **98,3 %** retrouvées ; les autres sont **exclues**, jamais placées approximativement.
- **Segmentation des PDF (D-008)** : comparée sur 408 contrats ; les **blocs** PyMuPDF (un bloc ≈ un
  paragraphe visuel) donnent 2 % de segments coupés au plafond, contre 18,8 % en texte brut.

### 3.6 Base de données de l'application (D-010)

- **PostgreSQL 17 + pgvector 0.8.7** dans **Docker** : image figée, accès local seulement,
  mot de passe aléatoire dans `.env` (jamais commité), données dans un volume.
- **Tables** : `contrats` (avec le texte complet), `pages`, `segments`, `resultats`. Les contraintes
  empêchent une provenance incohérente (fin avant début, page inexistante).
- **Test réel** : 408 contrats importés (96 244 segments), traçabilité vérifiée **en SQL** :
  0 erreur. pgvector est activé ; la colonne de vecteurs viendra avec F5.

### 3.7 Réentraîner sur les segments PDF (D-011)

## 4. Les notions, expliquées simplement

### Git et GitHub
- **Branche** : une copie de travail parallèle ; une branche par tâche (`exp/…`, `feat/…`).
- **Pull request (PR)** : une demande de fusion d'une branche dans `main`, qui permet la relecture.
- **Merge commit** (`--merge`) : la fusion garde tous les commits d'origine. On l'a préféré au
  *squash* (tout écraser en un commit), qui aurait cassé les PR empilées.
- **PR empilées** : la PR #3 partait de la branche de la PR #2. **Incident** : en supprimant la
  branche de la PR #2 à la fusion, GitHub a **fermé** la PR #3 (Claude avait annoncé à tort qu'elle
  basculerait vers `main`). Réparé sans perte. Leçon : changer la base de la PR suivante **avant**
  de supprimer la branche.

### Données et évaluation
- **Train / validation / test** : apprendre / régler / mesurer une seule fois.
- **Graine aléatoire** : un tirage « au hasard » reproductible ; fixée avant de tirer.
- **Empreinte** (MD5, SHA-256) : signature d'un fichier ; deux fichiers de même empreinte sont identiques.
- **Déséquilibre** : ~97 % des segments n'ont aucune famille. Un modèle qui répond toujours
  « aucune » aurait 97 % d'**exactitude** et ne servirait à rien : on ne regarde **jamais** l'exactitude.
- **Précision** : quand le modèle signale, a-t-il raison ? **Rappel** : trouve-t-il tout ?
  **F1** : compromis des deux. **Macro-F1** : moyenne des familles (la plus rare compte autant).
- **Rappel par annotation** : la clause annotée a-t-elle été trouvée ? Ne dépend pas de la
  segmentation, donc permet de comparer des segmentations différentes.
- **Significativité** : quand une annotation vaut un point, un écart d'un point ne prouve rien.

### Texte et traçabilité
- **Positions `[debut, fin)`** : la fin est exclue, comme en Python (`texte[debut:fin]`). En SQL,
  `substring(texte from debut + 1 for fin - debut)` (SQL compte à partir de 1).
- **Normaliser sans perdre la trace** : on compare des versions simplifiées des textes, mais chaque
  caractère simplifié garde la position du caractère d'origine.
- **Exact plutôt qu'approximatif** : pour la traçabilité, une annotation manquante vaut mieux qu'une
  annotation mal placée.

### Modèles
- **TF-IDF** : transforme un texte en nombres (un poids par mot, fort si le mot est fréquent dans
  le segment et rare ailleurs).
- **Régression logistique** : apprend un poids par mot et donne une probabilité ; **seuil** de
  décision réglé sur la validation. **Pondération des classes** : une erreur sur un segment rare
  coûte plus cher.
- **Baseline par mots-clés** : point de comparaison ; la liste est **figée avant** l'évaluation,
  sinon on « apprendrait » à la main sur la validation.

### Outils
- **pytest** : lance automatiquement les fonctions `test_*` ; certains tests sont « ignorés » si
  les données ou la base manquent (pour ne pas bloquer Ilyas).
- **MLflow** : garde les paramètres et métriques de chaque entraînement ; interface :
  `.venv/bin/mlflow ui --backend-store-uri sqlite:///mlflow.db` puis http://127.0.0.1:5000.
- **Docker** : fait tourner PostgreSQL dans un conteneur à partir d'une image figée ; **volume** =
  données conservées ; `docker compose down -v` les effacerait (à éviter).
- **Transaction** : tout le contrat est enregistré, ou rien.
- **`.env`** : les secrets, hors du dépôt ; `.env.example` : le modèle sans vraie valeur.

## 8. Proposition de présentation à l'encadrant (≈ 10 minutes)

1. **Le problème** (1 min) : lire un contrat en anglais, extraire 4 familles de clauses, toujours
   citer la source exacte, jamais donner d'avis juridique.
2. **Les données** (2 min) : CUAD (510 contrats, 41 catégories) ; les 3 découvertes de
   l'exploration ; ContractNLI pour la confidentialité.
3. **La rigueur** (2 min) : splits par contrat, test fermé et protégé dans le code, graine et listes
   figées avant évaluation, traçabilité testée (79 510 segments CUAD, 96 244 segments en base).
4. **Les résultats** (2 min) : mots-clés 0,25 → TF-IDF 0,67 (validation) ; la résiliation est la plus
   difficile et pourquoi ; ce que montrent les erreurs.
5. **L'architecture en place** (1 min) : PDF → segments avec page → base PostgreSQL ; démonstration
   possible (section 9).
6. **Les décisions à valider** (2 min) : surtout D-006 (ordre du planning), D-002/D-009
   (confidentialité), D-004 (test officiel).

**Questions probables** (réponses courtes) :
- *Pourquoi ne pas montrer de score de test ?* — Le test est ouvert une seule fois, à la fin de F2,
  avec une décision écrite ; sinon on le contamine.
- *Vos chiffres sont-ils comparables à l'article CUAD ?* — Non : même test, mais tâche différente
  (classer des segments par famille, pas retrouver des passages exacts sur 41 catégories).
- *Comment garantissez-vous la citation exacte ?* — Positions conservées partout, alignement exact,
  tests automatiques et vérification en SQL.
- *Pourquoi pas de négatifs CUAD pour la confidentialité ?* — 51 contrats de validation sur 61 ont
  des clauses de confidentialité non annotées : ce serait étiqueter de vraies clauses comme fausses.
- *Avez-vous utilisé une IA pour coder ?* — Oui, Claude Code, avec un mode d'exécution temporaire
  décidé et encadré ; chaque action est tracée dans `docs/JOURNAL_ACTIONS.md`, et toutes les
  décisions ont été prises par Sara.
